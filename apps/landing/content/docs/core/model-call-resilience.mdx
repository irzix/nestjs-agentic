---
title: Model Call Resilience
description: Retry with backoff and jitter, plus a circuit breaker that fails fast when a provider is down.
---

Provider SDKs retry internally, but that retry is invisible to the framework, applies only to that one adapter, and cannot be tuned per deployment. It also does nothing about a sustained outage: every request keeps waiting for its own timeout while a provider is down.

`resilience` adds a framework-level layer on top. Both halves are opt-in — with `resilience` unset, model calls are dispatched exactly as before.

```typescript
AgenticModule.forRoot({
  defaultModel: { provider: 'openai', model: 'gpt-4o' },
  resilience: {
    retry: { maxAttempts: 3, initialDelayMs: 250, maxDelayMs: 10_000, jitter: 0.5 },
    circuitBreaker: { failureThreshold: 5, cooldownMs: 30_000, successThreshold: 1 },
  },
});
```

## Retry

| Failure | Retried |
| --- | --- |
| `429`, `5xx`, network/timeout (no status) | Yes |
| Other `4xx` | No, a malformed request fails identically every attempt |
| `AgenticError` | No, it signals misconfiguration or an exceeded budget |
| `AbortError` | No, the caller cancelled |

Delay `n` is `initialDelayMs × 2^(n-1)`, capped at `maxDelayMs`, then randomized downward by up to `jitter`. At the default `0.5`, a computed 1000&nbsp;ms delay lands in 500–1000&nbsp;ms. Without jitter, every caller that failed in the same instant retries in the same instant, re-creating the spike that caused the failure.

A provider back-off hint wins over the computed delay, since the provider knows when its own quota resets. `retryAfterMs`, `retryAfterSeconds`, and the header-shaped `retryAfter` (seconds) are all read, and the result is still capped by `maxDelayMs`.

## Circuit breaker

```
closed ──[failureThreshold consecutive failures]──> open
open ──[cooldownMs elapsed]──> half_open
half_open ──[successThreshold successes]──> closed
half_open ──[any failure]──> open   (cooldown restarts)
```

While open, calls are rejected with `CircuitOpenError` — carrying `retryAfterMs` — without being dispatched.

The breaker sits **outside** the retry, so exhausting retries counts as one failure against the threshold: `failureThreshold: 5` means five genuinely failed calls, not five attempts inside one call.

State is per-process. Each replica detects an outage independently rather than paying a network round trip on the fail-fast path.

## Observability

```typescript
export class ResilienceObserver implements AgentObserver {
  onModelRetry(event: ModelRetryEvent) {
    metrics.increment('model.retry', { attempt: event.attempt });
  }

  onCircuitStateChange(event: CircuitBreakerEvent) {
    if (event.to === 'open') alerts.page(`${event.circuitName} opened: ${event.reason}`);
  }
}
```

Register with the `AGENT_OBSERVERS` token. Both hooks are optional, so existing observers need no changes.

## Notes

**Streaming.** A stream is retried only while nothing has reached the caller — the attempt covers opening it and pulling the first chunk. Past that, a retry would replay emitted tokens, so the error propagates.

**Cascading.** Resilience wraps the base adapter, so the cascade sits outside it. A retry re-attempts the failing tier rather than replaying the whole cascade and paying for its cheaper tiers again.

**Standalone use.** `retryWithBackoff`, `CircuitBreaker`, and `ResilientModelAdapter` are all exported for use outside the agent loop.
